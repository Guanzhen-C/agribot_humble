## 3. 当前软件架构实例

### 3.1 运行层次

可以在原文中补入以下描述：

> 当前导航软件采用分层、可配置的ROS 2架构。设备层完成C16机械式旋转激光雷达、IMU、工业相机、RTK及底盘通信接入；时间与坐标适配层完成设备时间映射、触发沿配对、传感器安装变换和定位参考点转换；算法层执行视觉激光惯性里程计、固定解RTK位置融合以及三维地图初始定位；导航层使用Nav2组织全局规划、局部代价地图、轨迹跟踪与目标执行；底盘适配层将车体速度目标转换为不同车型的控制报文。手机控制台承担任务启动、停止、地图选择和导航交互，运动控制和定位计算保留在车辆算力端。

当前主要数据流：

```text
C16 + IMU + 相机
       |
       v
    FAST-LIVO2 --> body/IMU位姿 --> 参考点桥接 --> /fastlivo/odometry
                                                     |
RTK位置 + 质量 + 地理配准 -----------------------------+--> 固定时滞因子图
IMU姿态提供重力方向 -----------------------------------+        |
三维地图 + 粗初值 --> NDT/GICP --> 初始地图位姿 ----------+        v
                                                   /fastlivo_rtk/odometry
                                                            |
二维地图 + 实时三维点云 --> Nav2代价地图 --> Smac --> MPPI --> Twist
                                                            |
                                                   车型底盘适配 + CAN
```

三维地图、二维栅格地图和实时局部点云承担不同职责：三维地图用于点云初始配准；二维地图用于Nav2全局规划；实时三维点云进入局部/全局代价地图的观测层。图示不表示用二维地图直接替代三维定位。

### 3.2 与通用ECU平台的关系

当前源码可以作为主流框架兼容、复杂设备驱动、车辆协议适配和智能导航算法的工程实例。HPM底层基础软件、柴油机控制、机具作业协议及硬件在环仍应由对应专业模块提供，不能用当前导航节点替代。

ROS消息接口与独立协议编解码能够减少模块耦合，但当前C++底盘抽象直接依赖 `rclcpp` 和ROS消息，不能未经裁剪就宣称适用于RT-Thread。若原文采用“公共算法核心+平台适配层”表述，应把已实现的ROS适配与待实现的嵌入式适配分开列出。

## 4. HUM-01：公共算法接口与组件

### 4.1 可补充的实际接口

算法层使用标准ROS消息作为主要数据契约：

| 对象 | 主要类型或入口 | 单位与含义 | 当前使用位置 |
| --- | --- | --- | --- |
| 激光观测 | `sensor_msgs/msg/PointCloud2` | 米；必须保留真实点云坐标系及点内时间含义 | 雷达驱动、定位、代价地图 |
| 惯性观测 | `sensor_msgs/msg/Imu` | 加速度m/s²、角速度rad/s、姿态四元数 | FAST-LIVO2、重力约束、NavSat ESKF |
| 图像 | `sensor_msgs/msg/Image` | 像素数据与采样/触发时间 | 工业相机驱动、FAST-LIVO2 |
| 卫星定位 | `sensor_msgs/msg/NavSatFix` | 纬度/经度为度，高度为米，带位置协方差 | RTK驱动与融合 |
| 位姿和速度 | `nav_msgs/msg/Odometry` | 位姿所属父坐标系、子坐标系及速度参考系明确 | 定位桥接、融合、Nav2 |
| 路径 | `nav_msgs/msg/Path` | 同一地图坐标系中的有序位姿 | 规划、可视化 |
| 车体目标 | `geometry_msgs/msg/Twist` | `linear.x`为m/s，`angular.z`为rad/s | Nav2至底盘适配 |
| 就绪状态 | `std_msgs/msg/Bool` | 表示发布者定义的当前就绪条件 | 融合与底盘许可检查 |
| 诊断 | `diagnostic_msgs/msg/DiagnosticArray` | 状态、计数、时间来源等诊断信息 | 驱动、融合、CAN、控制台 |

这些类型统一了接口形式，但没有替代坐标、时间、质量、超时和生命周期约定。尤其 `Twist` 本身没有时间戳和来源标识；相关限制见 HUM-06、HUM-11。

### 4.2 两类底盘共用源码的实际对照

当前底盘实现已采用“共用节点和传输层+车型适配器”结构：

| 共用/专用部分 | 阿克曼实例 | 履带差速实例 |
| --- | --- | --- |
| 节点调度与健康检查 | 共用 `can/src/chassis_can_node.cpp` | 同左 |
| SocketCAN/ZQWL通信 | 共用 `can/src/chassis_can_transport.cpp` | 同左 |
| 数值编码工具 | 共用 `can/src/chassis_can_common.cpp` | 同左 |
| 车型适配 | `ackermann/src/ackermann_chassis_adapter.cpp` | `differential/src/differential_chassis_adapter.cpp` |
| 协议编解码 | `ackermann/src/ackermann_can_protocol.cpp` | `differential/src/differential_can_protocol.cpp` |
| 创建入口 | `makeAckermannChassisAdapter` | `makeDifferentialChassisAdapter` |

以上路径均位于 `src/agribot_hardware_bringup/`。

公共头文件 `can/include/agribot_hardware_bringup/chassis_adapter.hpp` 定义：

```cpp
struct MeasuredMotion {
  double linear_velocity;
  double angular_velocity;
};

struct FrameUpdate {
  bool valid;
  bool checksum_error;
  std::optional<bool> emergency_stop;
  std::optional<MeasuredMotion> motion;
};
```

`ChassisAdapter` 提供 `commandId`、`feedbackIds`、`commandFromTwist`、`processFrame`、`feedbackFresh`、`feedbackAllowsMotion` 和 `populateStatus` 等方法。`FrameUpdate.valid` 不能单独理解为已得到完整车体运动反馈；只有 `motion` 存在时才有本次完整运动测量结果。

传输接口 `ChassisCanTransport` 提供 `restart`、`writeFrame` 和 `readFrames(max_frames)`，把底盘协议与实际CAN设备访问分开。共用CMake目标与两个专用库的链接关系可在 `src/agribot_hardware_bringup/CMakeLists.txt` 核对。

## 7. HUM-04：观测器、定位和反馈来源

### 7.1 实际测量来源与输出参考点

当前主定位链使用C16点云、Hipnuc IMU及工业相机生成FAST-LIVO2里程计，再结合RTK固定解位置构建外部因子图。传感器测量、算法估计和底盘反馈分开记录：

| 数据 | 来源 | 性质与限制 |
| --- | --- | --- |
| `/lidar/points` | C16驱动 | 激光原始观测，不是定位真值 |
| `/imu/data` | IMU驱动 | 加速度、角速度及设备姿态；不是整车真值 |
| `/camera/rgb/image_raw` | 工业相机驱动 | 图像观测；运动估计仍依赖算法 |
| `/rtk/fix` | RTK串口解析 | 主天线位置，非直接等于base_link位置 |
| `/aft_mapped_to_init` | FAST-LIVO2 | 算法body/IMU参考点的里程计 |
| `/fastlivo/odometry` | 位姿桥接 | 转换到车辆base_link的局部里程计 |
| `/fastlivo_rtk/odometry` | 外部融合节点 | 地图坐标下融合后的车辆状态 |
| `/wheel/odometry` | 底盘反馈积分 | 独立轮速里程计；不等于激光定位 |

阿克曼的 `base_link` 位于后轴中心；履带差速的 `base_link` 使用名义接地/滑移转向中心的地面投影。传感器在各自参考点测量，算法输出需经过安装变换才能供整车控制使用。

设 `T_world_body` 为算法body位姿、`T_base_body` 为传感器安装位姿，则：

```text
T_world_base = T_world_body * inverse(T_base_body)
```

不能只更改Odometry中的字符串 `child_frame_id` 而不转换平移、旋转及相关速度量。

依据：`src/agribot_hardware_bringup/config/fastlivo_bridge.yaml` 和 `localization/fastlio/scripts/fastlio_odom_bridge.py`。配置指明保留输入时间戳、将body位姿转换为base_link，并可发布 `odom -> base_link`。

### 7.2 FAST-LIVO2+RTK外部融合

实现入口：`src/agribot_hardware_bringup/localization/fusion/src/fastlivo_rtk_fusion_node.cpp`。

该节点使用GTSAM增量固定时滞平滑器。FAST-LIVO2的相邻关键帧位姿形成相对运动约束；质量合格的RTK观测经地理配准和天线杆臂建模后形成水平位置约束；IMU姿态提供重力方向约束，限制横滚和俯仰。该外部后端不直接修改FAST-LIVO2内部估计器状态。

基础配置 `src/agribot_hardware_bringup/config/fastlivo_rtk_fusion.yaml` 的关键条件：

| 参数 | 当前配置 | 含义 |
| --- | --- | --- |
| `required_fix_quality` | 4 | 运动中的RTK位置因子只使用固定解 |
| `required_consecutive_fixed` | 3 | 建立固定解可用状态所需连续观测数 |
| `fixed_lag_sec` | 60.0 s | 限制图中活动状态的时间范围 |
| `keyframe_period_sec` | 0.50 s | 关键帧触发条件之一 |
| `keyframe_distance_m` | 0.30 m | 关键帧位移条件之一 |
| `keyframe_angle_rad` | 约5° | 关键帧转角条件之一 |
| `rtk_horizontal_sigma_floor_m` | 0.10 m | 水平噪声下限，还结合地理配准误差 |
| `rtk_max_innovation_m` | 1.50 m | RTK创新检查配置值 |
| `odom_ready_timeout_sec` | 0.50 s | FAST-LIVO2输入停滞时撤销融合就绪 |
| `preserve_local_vertical` | true | 保留局部里程计相对高度，不把RTK XY当作Z约束 |

RTK退出固定解后停止加入相应位置因子，按配置冻结全局修正并依靠FAST-LIVO2局部里程计继续传播。这是已有退化处理逻辑，不表示卫星失效期间定位误差不会增长。

融合状态和TF仍是三维的；`flatten_visualization_paths: true` 仅平面化三条显示轨迹。不能根据RViz轨迹的Z为零推断实际Odometry和TF为二维。

### 7.3 初始化与NavSat备选定位

主真机运行入口支持RTK、视觉和手动粗初值；粗初值再进入三维点云NDT/GICP配准。航向质量条件用于粗定位初始化时，不应与“运动中只接受固定解RTK水平位置因子”混为一谈。具体条件必须以车型Launch及初始化配置为准。

NavSat备选定位的入口是 `rtk_eskf_localization_node.cpp`、`rtk_gi_engine.cpp`，输出 `/odometry/filtered_navsat`。其配置说明了BLH/局部参考点、ENU/NED转换、IMU输入、RTK航向、初始化和杆臂。

应准确表述为“基于KF-GINS的源码子集及项目ROS封装/扩展”，而不是“完整官方KF-GINS程序原样运行”。当前内置子集包含地球模型、旋转、导航类型和惯导机械编排；测量更新及ROS集成在项目引擎和节点中实现。依据：`localization/navsat/third_party/kf_gins/README.md`、`config/kf_gins_n300pro.yaml`。

### 7.4 底盘速度反馈的可解释范围

阿克曼反馈报文直接解析出车体线速度、车体角速度及惯性量。解析器不能证明这些量在底盘固件中来自编码器、转角传感器还是运动学计算；`angular_velocity_z` 与 `imu_angular_velocity_z` 是不同字段。

履带差速反馈包含电机转速，配置文件已注明从电机RPM到履带线速度的比例仍为可选轮速里程计的临时值。不能把这个比例当作完整传动、履带打滑标定结果。

仍缺：编码器读取和采样的主体说明、传动比/有效半径、真实转向测量链、反馈时间基准，以及独立定位参考下的误差统计。这些材料应由底盘固件及试验组提供。

## 8. HUM-05：本地保护与独立停车

### 8.1 当前算力端已经实现的检查

CAN共用节点在发送前检查命令是否新鲜、反馈是否新鲜和允许运动、是否满足定位就绪要求；不满足条件时通过车型适配器构造零运动目标。ROS正常关闭前还会尝试发送停车帧。发送异常被记录为错误，不能据此推断底盘收到停车请求。

这些属于算力端的请求与保护检查，不能替代独立停车证明：

- 进程收到停止或退出命令，不等于车轮已停止。
- `writeFrame` 成功是本地通信受理，不等于底盘执行确认。
- CAN线断开时，算力端发出的零帧可能无法到达控制器。
- 阿克曼解析器保留 `stop_flag` 原始值，但本轮未取得其完整固件枚举及对应动作，不能自动写为安全急停语义。
- 当前健康检查恢复后，若命令仍符合新鲜性等条件，不能认定已有“必须人工复位且必须复位后新目标”的锁定机制。

### 8.2 无法补齐的硬件及固件材料

应继续索取：独立急停回路图、底盘失联期限、零目标的减速/制动语义、转向回正或保持规则、坡道载荷试验、急停解除及重新授权流程，以及通信断开/程序崩溃/算力端掉电时的实际停车记录。当前软件检查可以写入正文，但 HUM-05 不应据此关闭。

`src/agribot_mobile_app/agribot_mobile_app/gateway_node.py` 的 `start_runtime` 使用任务转换锁，在启动新任务前调用 `_stop_active_tasks`。该方法取消已有导航，停止由进程管理器管理的任务，检查旧任务是否全部退出，再清理旧状态；如果仍存在受管理的运行任务则拒绝启动新任务。`stop_runtime` 会取消导航并停止当前运行任务。

### 9.3 仍不能填写为已完成的内容

阿克曼适配器没有已确认的无人/人工模式反馈语义；`feedbackAllowsMotion(require_autonomous_mode)` 在要求无人模式时不会假造一个可用的模式值。履带底盘已有模式和故障解析，但整个车辆的遥控、蓝牙、导航和调试优先级仍须结合真实固件确认。

手机网络断开与车辆内部CAN/定位链失效是两类事件。任务在车辆算力端执行，不能把手机在线状态当成定位真值或硬件急停。需要由项目明确两类事件的运行策略，而不是根据前端页面状态推定。

### 12.3 幅值限制与变化率应分别说明

`fromTwist` 检查有限数值和正参数，并对车速、角速度及转角限幅；低于最小运动速度时输出零运动。`limitSteeringRate` 函数及其单元测试已存在，串口节点使用该函数，但当前阿克曼CAN适配器的目标转换链没有调用它。

当前源码也不能直接替代原说明书拟定的 `ControlCore` 锁定故障、人工复位、恢复后新命令资格机制。其代码和测试需独立交接，不能以这里的实时健康检查冒充。

### 14.3 真实时间链

> 当前车辆端将绝对时间与采样相位分别处理。RTK的TTL时间报文提供绝对日期/时刻，PPS提供秒边界，配合本地授时服务校准系统时钟；C16通过专用以太网链路使用gPTP，激光驱动解析设备时间并可使用首点时间作为整云时间戳；相机由PPS锁相的PWM触发，另一路GPIO捕获每个真实上升沿，驱动将收到的相机帧与触发沿对应；IMU使用设备采样计数经仿射时钟映射转换为平台时间。不同设备的采样时间、传输到达时间和程序处理时间分别记录。

### 14.4 当前触发方案的准确边界

`camera_trigger_pwm.env` 当前选择 `pin32_pwm`，名义周期100 ms、高电平1 ms；Pin33记录每个实际上升沿。保留的 `j14_lpwm` 后端用于未来接线，不是当前运行后端。因此应写为“PWM输出、PPS软件锁相、GPIO真实沿时间戳”，不能把当前方案写成已启用J14硬件锁相。

相机驱动可配置设备时间或接收时间；硬触发和物理沿匹配开启时优先按物理沿赋戳。非硬触发时的设备仿射映射与主机接收时间是另一种策略，报告需保存实际启用参数。

当前gPTP配置对C16的UTC/PTP秒解释作了设备适配，`utc_offset: 0` 等值不能不加验证地移植到其他固件或其他PTP设备。室内无卫星时的持续输出、保持时间和PPS恢复策略也不等于系统时间绝对精度永远不变。

基础FAST-LIVO2配置注释登记了一次2026-08-22相位测试：相机戳比C16正前方点早约3.263 ms、P95约3.375 ms，并配置 `img_time_offset: -0.0033`。本轮只核对源码注释，没有重新取得该次原始时序日志；应列为历史标定记录，不能作为当前接线的复测结论。

### 14.5 多线程与有界缓存

当前FAST-LIVO2的接收、点云预处理和状态估计不再全部串行在一个回调线程内。`src/FAST-LIVO2/src/main.cpp` 使用3线程 `MultiThreadedExecutor` 接收回调，并单独运行估计循环；`src/FAST-LIVO2/src/LIVMapper.cpp` 创建点云预处理线程。雷达、IMU与图像分别使用独立回调组；图像和点云内部队列设有边界，负载超限时丢弃旧输入，降低无限积压风险。

基础配置 `src/FAST-LIVO2/config/agribot_c16_astra.yaml` 登记：

| 缓存/处理参数 | 配置值 |
| --- | --- |
| 图像订阅深度 | 2 |
| 内部图像缓存上限 | 3 |
| 雷达订阅深度 | 4 |
| 原始雷达输入缓存上限 | 4 |
| 已预处理雷达缓存上限 | 2 |
| IMU订阅深度 | 200 |
| 内部IMU缓存上限 | 300 |
| 算法图像处理最高频率 | 10 Hz |

驱动层、DDS层、内部算法队列和录包缓存是不同层次，不能以一个队列上限推断整机总延迟上限。丢弃旧帧能控制积压，但持续丢帧依然是实时能力不足，需要统计接收、处理和丢弃数量。

## 15. HUM-12：真实通信、正式头文件与部署

### 15.1 通信后端

当前不是仅有Mock协议。`can/src/chassis_can_transport.cpp` 包含SocketCAN和智嵌物联ZQWL CDC设备访问；头文件在 `can/include/agribot_hardware_bringup/chassis_can_transport.hpp`。

传输配置包含后端、CAN接口、USB设备路径、通道和波特率。ZQWL协议封装有22字节参数包、16字节经典CAN包及流式解码器。阿克曼基础波特率1 Mbit/s、履带差速基础250 kbit/s，不能跨车型直接复制。

设备名称包含“CANFD”不表示实际下发帧就是CAN FD。这里的底盘接口使用8字节经典CAN数据，不应仅根据USB设备型号改写协议类别。

### 15.2 阿克曼正式控制协议

正式头文件：`ackermann/include/agribot_hardware_bringup/ackermann_can_protocol.hpp`；实现见同目录体系下 `src/ackermann_can_protocol.cpp`。

| 内容 | 当前编码 |
| --- | --- |
| 控制ID | 0x181 |
| 数据长度 | 8字节 |
| Byte 0—1 | 有符号车速，0.001 m/s/LSB，大端 |
| Byte 2—3 | 保留，0 |
| Byte 4—5 | 有符号中心转角，0.001 rad/LSB，大端 |
| Byte 6—7 | 保留，0 |
| 反馈ID | 0x101、0x102、0x103 |
| 完整反馈 | 合并24字节，检查帧头0x7B、异或校验及帧尾0x7D |

`fromTwist(v, omega, ...)` 使用 `atan(wheelbase * omega / v)` 转换中心转角，配合速度、角速度、转角限制与低速零运动分支。Nav2给底盘的 `angular.z` 是角速度，不能把它直接当作前轮角度使用。

独立字节样例可补入附录A：

```text
v=0.0 m/s，delta=0.0 rad：00 00 00 00 00 00 00 00
v=0.1 m/s，delta=0.0 rad：00 64 00 00 00 00 00 00
v=-0.1 m/s，delta=0.0 rad：FF 9C 00 00 00 00 00 00
v=0.1 m/s，delta=-0.12 rad：00 64 00 00 FF 88 00 00
```

反馈解析还包括车体横向速度、角速度、加速度、IMU角速度和电压。其物理来源不能只根据字节解析推断。

完整24字节反馈的数据布局可以按当前解析器补入附录A，索引从0开始：

| 字节 | 字段 | 解析方式 |
| --- | --- | --- |
| 0 | 帧头 | 固定0x7B |
| 1 | `stop_flag` | 原始无符号值；动作枚举仍待固件确认 |
| 2—3 | 车体X线速度 | 大端有符号16位，乘0.001，单位m/s |
| 4—5 | 车体Y线速度 | 同上 |
| 6—7 | 车体Z角速度 | 大端有符号16位，乘0.001，单位rad/s |
| 8—13 | X/Y/Z加速度 | 每轴大端有符号16位，除以1671.84，单位m/s² |
| 14—19 | IMU X/Y/Z角速度 | 每轴大端有符号16位，乘0.00026644，单位rad/s |
| 20—21 | 电压 | 大端无符号16位，乘0.001，单位V |
| 22 | 校验 | 前22字节逐字节异或 |
| 23 | 帧尾 | 固定0x7D |

解析失败返回空结果，不产生新的完整测量。源码中的 `DecodesCapturedC50cTelemetry` 使用固定捕获样本进行字段测试；此测试样本可用于确定性规程，但不替代本轮真实总线抓帧。

### 15.3 数值编码的正式定义

`can/src/chassis_can_common.cpp` 中 `scaledInt16(value, units_per_raw)`：

1. 拒绝NaN/Inf输入。
2. 拒绝非有限或非正编码分辨率。
3. 对 `value / units_per_raw` 四舍五入。
4. 饱和到有符号16位整数范围。

字节序由具体协议实现，公共工具中的小端函数不能据此推断阿克曼也是小端。分辨率量化、限幅和算法参数容差应分别记录。

### 15.4 履带差速协议实例

当前三合一底盘协议使用0x514控制、0x532底盘状态、0x533左电机、0x534右电机反馈，包含模式、故障、急停、电压、电机转速等解析。依据：`differential/include/agribot_hardware_bringup/differential_can_protocol.hpp` 和对应实现/测试。

该协议仅用于说明公共适配层的另一个实例，不替换原说明书中的阿克曼固定协议。

### 15.5 ROS QoS与多实例边界

CAN共用节点实际配置：命令订阅深度20，轮速Odometry发布深度20，状态发布深度10；定位就绪订阅使用深度1、Reliable、Transient Local；诊断采用SystemDefaultsQoS。

## 18. HUM-15：现场与整机验收

### 18.1 可补入的试验规程

当前项目支持依据同一车型配置、地图和算法组合组织以下现场试验，但下列规程不表示已经全部执行：

1. 记录车体、附件、载荷、轮胎/履带状态、接线、软件和配置指纹。
2. 测量场地、路线、通道宽度、坡度、地表及障碍物，标记监督接管和独立停车方式。
3. 静置检查全部设备、时间同步、有效外参、CAN完整反馈及地图文件。
4. 关闭底盘输出，验证粗定位、NDT/GICP精配准、融合就绪、TF及规划结果。
5. 在允许的受控场地开启低速运动，执行直线、转弯、连续途经点和受控障碍绕行。
6. 分别检查目标取消、定位输入中断、反馈中断、程序退出、人工接管和硬件急停；高风险情况需采用专门台架或受控工况。
7. 保存目标、Path、实际Odometry、CAN抓帧、传感器/触发日志、独立参考、事件及失败复验记录。
8. 由责任人按预先确定的判据签署结果，不以“看起来正常”替代误差和停车响应统计。

### 18.2 精度证明的独立性

若RTK已参与融合，不能只用同一RTK观测证明融合算法的绝对精度。需要独立测量或独立参考区间；用于地理配准拟合的数据与验证数据也应分开，避免把拟合残差当定位泛化精度。

仍需现场组给出独立参考方法、重复次数、误差和停车通过条件、实测场地表及正式记录。原合同涉及的果园或农机具工况不能只由走廊/园区导航替代。
